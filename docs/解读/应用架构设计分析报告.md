# DeepSeek Harness 应用架构设计分析报告

> 阅读日期：2026-09-21  
> 这份笔记讲**应用怎么分层、一轮对话怎么走、界面和外部程序怎么接到同一内核**。  
> 不重复「目录怎么放、命令怎么敲」——那部分见 [脚手架分析报告](./脚手架分析报告.md) 和 [运行模式分析报告](./运行模式分析报告.md)。  
> 依据：`docs/architecture.md`、`docs/cordis-primer.md`、`packages/host/README.md`、`packages/client/README.md`。  
> 性质：解读笔记，非产品权威。

## 先记住这一段

DeepSeek Harness 的应用设计可以收成四条：

1. **内核只有一份**：会话、主循环、工具、模型、文件和命令执行，都跑在同一个 Node 进程里的插件树上（框架叫 Cordis：插件往共享上下文注册服务和事件）。  
2. **给模型看的内容必须能从会话日志还原**。界面上的流式字是临时的；真正落盘、可回放的是会话事件。  
3. **网页、桌面、SDK、无界面任务是不同「外壳」**，不是四套 Agent。外壳负责收发消息；干活的还是同一套主循环。  
4. **新能力默认挂到已有扩展点**（新工具、新模型适配器、新界面卡片），而不是改主循环。

```text
用户 / 外部程序
    │
    ├── 浏览器界面（Client）──WebSocket──► 本机服务（Host）
    ├── 桌面壳（Electron）──同一套网页 + 本机服务
    ├── SDK / ACP ──标准输入输出上的协议──► 同一内核
    └── 无界面命令 ──直接把任务交给主循环
                        │
                        ▼
              主循环（一次模型请求 + 它调用的工具）
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
       会话日志      模型适配器      工具与执行
     （本地真相）   （DeepSeek 等）  （文件/命令/沙箱）
```

## 1. 设计上分成哪几层

| 层 | 白话 | 主要代码位置 |
| --- | --- | --- |
| 外壳 | 人怎么交互：网页、桌面窗口、命令行一次任务、SDK/ACP | `packages/client/`、`apps/desktop/`、`packages/bundle/headless`、`packages/sdk/`、`packages/acp/` |
| 本机服务 | 给浏览器提供页面、认证和远程调用 | `packages/host/`、`packages/api/` |
| 主循环 | 收用户输入、问模型、执行工具、再问，直到这一轮结束 | `packages/core/agent`、`packages/core/agent-loop` |
| 能力 | 模型能用的工具，以及背后的文件、命令、终端、沙箱 | `packages/fs/`、`shell/`、`sandbox/` 等 |
| 记录 | 只追加的会话日志；模型历史从日志推出来 | `packages/core/session`、`packages/session/` |

外壳可以换，主循环和会话日志不随外壳复制一份。

## 2. 内核：插件共享一个上下文

运行时不是「一个大类里写死所有功能」，而是很多插件挂在同一上下文上。别人通过固定名字找服务，例如：

| 名字 | 干什么 |
| --- | --- |
| `ctx.sessions` | 会话日志与内存视图 |
| `ctx.agents` | 当前活着的 Agent（一次会话里的执行者） |
| `ctx.agentLoop` | 默认主循环实现（可以换实现，接口仍在 `ctx.agents`） |
| `ctx.llm` | 模型适配器（DeepSeek 等） |
| `ctx.tools` | 工具注册与执行流水线 |
| `ctx.systemPrompt` | 拼系统提示和工具描述 |

插件声明自己依赖哪些服务，等服务就绪再启动，而不是手写「谁必须先启动」。  
注册（工具、监听）应能在插件卸载时撤销。

三类事件（改功能时先选对类）：

| 类型 | 何时用 | 例子 |
| --- | --- | --- |
| 会话事件 | 必须重启后还能还原、并且可能给模型看 | `user/message`、`assistant/message`、`tool/call` |
| Agent 事件（`agent/…`） | 任务进行中观察或拦截 | 一步开始前、请求发出前 |
| 能力事件（`fs/…`、`tools/…`） | 给文件、工具加策略，不必改主循环 | 工具执行前检查 |

有一类「包一层再交给下一环」的事件：监听函数必须调用 `next()`，否则等于截断后续逻辑。

## 3. 一轮对话怎么走

两个词：

- **一步（step）**：一次模型请求，加上这次请求里调用的工具。  
- **一轮（turn）**：从认领用户输入开始，到不再欠模型或工具任何事为止；里面可以有零步或多步。

简化顺序（完整步骤见 `docs/architecture.md` 的 Turn flow）：

1. 开始一轮，认领下一条用户输入。  
2. 拼系统提示和工具列表。  
3. `agent/pre-step` 可以改写或拒绝输入；若第一次就被拒或改成空，这一轮结束且没有模型调用。  
4. 向模型发请求（可取消；取消时这一步不把系统提示和用户消息提交进日志）。  
5. 从**会话日志**推出模型要看的历史，再流式接收回答。  
6. 若模型要调工具：执行前 → 执行 → 执行后 → 把结果写入日志。  
7. 若工具结果还需要再问模型，或又来了新输入，进入下一步。  
8. 结束这一轮。

设计约束：

- 写入日志的有：轮次、步骤、系统/用户/助手消息、工具调用与结果。  
- 流式过程（`agent/assistant-stream`）主要给网页实时显示；进程在「这一步还没结算」时崩溃，磁盘上可能没有这段流。  
- 重试不会把「拼提示」和「决定是否进入」再做一遍。

---

## 4. 会话日志是模型上下文的来源

模型看到的历史由 `deriveMessages()` 从会话日志推出来，而不是界面自己记一份「真历史」。

因此：

- **任何会进入模型请求的新内容，都要有对应的会话事件。**  
- 只影响「怎么画卡片」的状态，不要写进日志。  
- 助手最终内容写在 `assistant/message` 里；失败、取消、重试等尝试可以记 `assistant/attempt`，但不进入模型历史。  
- 日志文件按代保存（如 `session.vN.jsonl`，可选压缩）。旧文件不改名、不覆盖、不删除；读的时候选最高代，需要写入时再在旁边发布下一代。

另有「投影」：把已提交事件折成界面或查询用的状态（`ctx.sessionProjections`）。它是日志的派生视图，不是第二份真相。

## 5. 可替换能力：接口、实现、使用方

一项可换的能力通常要三块一起设计：

1. **接口**：规定能调什么。  
2. **实现**：本机或远程真正干活。  
3. **使用方**：常常是给模型调用的工具。

换实现时，整条链一起换。例如把文件和子进程指到远程沙箱，命令行、终端、语言服务会一起走远程，而不是各写一套分叉。

常见落点：`ctx.fs`、`ctx.subprocess`、`ctx.shell`、`ctx.terminals`、`ctx.sandbox`、`ctx.llm`、`ctx.tools`。

## 6. 网页：本机服务 + 浏览器，单向分层

网页不是「React 里直接调模型」。分成两半：

| 半边 | 跑在哪 | 干什么 |
| --- | --- | --- |
| Host（本机服务） | Node | HTTP、静态页面、工作区选择、认证后的远程调用 |
| Client（浏览器） | 浏览器 | 聊天、设置、审批、文件树等界面插件 |

浏览器通过 WebSocket 和类型化远程调用（仓库里叫 Typert）跟 Host 说话。  
桌面版不重写这套界面：Electron 窗口加载同一套网页，并连到本机已认证的 Host。

浏览器端再分成三层，知识只能往下看、不能反过来：

| 层 | 规则 |
| --- | --- |
| 数据对象 | 会话、连接等状态在这里；不依赖 React |
| 渲染机制 | 把数据和插槽绑到 React |
| 展示组件 | 只收属性画界面；不直接摸运行时上下文 |

新的一块界面，优先注册「对话节点」和对应渲染，而不是在总会话类里加一个大分支。产品文案走语言包，不写死在组件里。

## 7. 其它外壳怎么接到内核

| 外壳 | 接到内核的方式 |
| --- | --- |
| 网页 / 桌面 | Host 调 `ctx.agents`，界面按会话事件和流式事件刷新 |
| 无界面一次任务 | 同一主循环；打出最终答案后退出 |
| TypeScript / Python SDK | 再启动一个 `dsh --profile sdk`（或最小版），用标准输入输出上的 JSON-RPC |
| ACP | `dsh --profile acp`，协议不同，内核仍是同一套 Agent |

SDK **不**在调用方进程里再嵌一整棵插件树。

人可以直接下的命令（不经过一轮模型）走 `ctx.commands`。  
外部 Webhook 在规则允许时，可以创建工作区会话，而不是绕过会话日志另开一条隐式对话。

## 8. 安全与执行放在哪

| 关注点 | 设计位置 |
| --- | --- |
| 这一步能不能执行、要不要人批准 | 权限预设 + 工具执行前后事件 |
| 进程能碰哪些路径、能不能出网 | `ctx.sandbox`；调用方在真正启动进程前包装命令行 |
| 文件读写策略 | `ctx.fs` 与 `fs/…` 事件 |
| 网页只给本机开 | 默认绑本机地址；禁止 `0.0.0.0`（见网页启动说明） |
| 密钥 | 放在凭证/设置里，不写进会话事件，因此默认也不会进遥测副本 |

## 9. 加功能时优先改哪里

| 你想做的事 | 挂哪里 |
| --- | --- |
| 新的模型提供方 | `ctx.llm` |
| 新的模型工具 | `ctx.tools`（描述会进入提示词组装） |
| 某个会话用另一套工具 | Agent 预设；需要隔离的服务行用隔离域 |
| 拦请求、拦工具、结束一轮 | `agent/…` 或 `tools/…` 事件 |
| 长期保存、且模型或回放要用 | 扩展会话事件类型 |
| 网页上一块新卡片 | Client 的对话节点 + 渲染 |
| 换会话存储介质 | 实现 `SessionPersistence`（创建/打开/列举/导出） |
| 只给某一个 Agent 注册 | 用该 Agent 自己的 `agent.ctx` |

**默认不要改 `agent-loop`。** 若必须改主循环，同一变更要更新 `docs/architecture.md`。
