# DeepSeek Harness 脚手架分析报告

> 阅读日期：2026-09-21  
> 这份笔记回答三件事：**代码怎么放、程序怎么启动、新功能往哪加**。不是功能说明书。  
> 依据主要来自：`docs/architecture.md`、`docs/cordis-primer.md`、`packages/README.md`、`packages/boot/app-boot/README.md`、`vendor/README.md`，以及根目录的 `package.json`、`pnpm-workspace.yaml`。若与官方文档冲突，以官方文档为准。

## 先记住这一段

DeepSeek Harness（简称 dsh）是一个用 **pnpm 管理的多包仓库**。几乎所有能力都做成 **插件**，由框架 **Cordis** 装进同一个运行环境。

启动时不是跑一个写死的大程序，而是：

1. 选一个启动配置（仓库里叫 **profile**，可理解为「产品形态」：网页版、无界面版、SDK 版等）；
2. 按顺序叠几层配置补丁（仓库里叫 **bundle** / **patch**）；
3. 再叠上用户自己的修改和命令行参数。

**正式支持的启动方式只有：**

```sh
dsh --profile <名称>
# 或简写
dsh <名称>
```

不要指望用某个包自带的小命令、演示脚本，或 SDK「在进程里直接挂插件」来当正式应用入口。仓库里有检查脚本专门拦住这类旁路。

## 1. 顶层目录各自干什么

| 目录 | 通俗说明 |
| --- | --- |
| `packages/` | 几乎所有功能包；路径是 `packages/分组/包名/`，npm 名是 `@deepseek-ai/dsh-…` |
| `apps/` | 真正面向用户的产品壳：`cli`（命令行 `dsh`）、`web`（网页前端构建与测试）、`desktop` / `desktop-host`（桌面 Electron 应用） |
| `vendor/` | 把 Cordis 等框架的**源码拷进仓库**，方便审计和打本地补丁，并改成 `@deepseek-ai/…` 名字 |
| `python/` | Python 客户端；默认再拉起 `dsh --profile sdk`，不是在 Python 里重写一套 Agent |
| `native/` | 需要系统能力的本地模块（例如 Linux 沙箱启动器、文件锁） |
| `scripts/` | 构建、检查、生成文档目录、发版等脚本；CI 会批量跑它们 |
| `docs/` | 架构说明、教程、子系统参考、用户文档 |
| `.agents/` | 给人用的决策笔记（`notes/`）和可复用操作流程（`skills/`） |
| `website/` | 文档网站；**正文仍在 `docs/`**，网站只是按名单把文档投影出去 |
| `snapshots/` | 录好的会话回放测试；必须走正式的 `dsh` + 出厂 profile |
| `benchmarks/` | 性能测试相关 |
| `patches/` | 对第三方依赖打的补丁（例如终端库、Electron 相关） |

多包范围写在 `pnpm-workspace.yaml`。需要 **Node.js 22.19+ 或 24+**，包管理器用 **pnpm 11.7.0**。

## 2. 启动配置怎么叠起来（profile / bundle / patch）

### 2.1 用三明治理解

跑起来的 `dsh` 可以想成一张从空开始往上叠的配置单：

```text
空列表（什么插件都还没有）
  → 按 profile 声明的顺序，叠每个「功能包组合」的补丁文件
  → 再叠这个 profile 目录里用户的 cordis.patch.yml
  → 再叠用户主目录（$DSH_HOME）里的 cordis.patch.yml（这一层盖过上一层）
  → 再叠命令行 --patch 指定的临时补丁
```

几个词的白话意思：

| 词 | 白话 |
| --- | --- |
| **profile** | 一种启动形态。文件在 `$DSH_HOME/profiles/<名字>/`，里面写「用哪些功能包组合」，以及你自己的配置补丁。 |
| **bundle** | 可安装的一层功能组合：自带一份 `cordis.patch.yml`，并带上实现代码。例如 `dsh-base` 是共用底座。 |
| **patch** | 按插件行的 **id** 整行替换配置，或插入新行。**不会**和旧配置做字段级合并。YAML 里的 `!!js` 只用于少数字段（配置值、是否禁用），在启动时算一遍。 |
| **预览** | `dsh --profile web --dump-config` 只打印「最终会装哪些插件」，不真正跑业务。 |

细节见 `docs/architecture.md` 与 `packages/boot/app-boot/README.md` 里的 Profiles 一节。

### 2.2 出厂有哪些 profile

| 名称 | 大致由什么组成 | 用来干什么 |
| --- | --- | --- |
| `web` | 共用底座 + 网页应用层 | 浏览器里用的界面（默认常开本地网页） |
| `headless` | 共用底座 + 无界面运行层 | 跑完一次任务就结束，不开网页服务 |
| `sdk` | 共用底座 + SDK 服务层 | 给外部程序用的 JSON-RPC 服务 |
| `acp` | 共用底座 + ACP 层 | 自动化协议，走标准输入输出 |
| `sdk-minimal` | **只有**最小 SDK 组合 | 故意不加共用底座，树更短、更显式 |
| `desktop` | 桌面应用专用名 | **命令行不能**拿它当普通 profile 启动/管理 |

`dsh-base`（`packages/bundle/base/cordis.patch.yml`）是网页 / 无界面 / SDK / ACP 共用的第一层：大模型接入、工具、会话存储、沙箱、设置、凭证、热更新与插件管理等。不同形态差异大的配置**不写进底座**，由各自的应用层整段改写，避免互相打架。

想看「默认到底装了哪些行」，可对照 `apps/cli/composition.md`（由脚本生成）。

### 2.3 从敲命令到进程起来

1. 开发时根目录脚本：`node --import tsx/esm apps/cli/src/bin.ts`（用 tsx 直接跑 TypeScript）。
2. `apps/cli` 解析参数，加载对应启动逻辑；发布后命令是 `@deepseek-ai/dsh`。
3. `dsh-app-boot` 读环境变量文件、叠补丁、用 Cordis 的加载器挂插件；**必选插件**挂不上就整棵树拆掉并以失败码退出。
4. `dsh-cmdline` 把启动命令后面的参数交给已经起来的应用。

可选插件挂失败：多半只警告。必选插件挂失败：停止启动。必选名单覆盖 Agent 主循环、网页服务、无界面 runner、ACP、SDK 服务等（见 app-boot 说明）。

硬规则（架构文档 Application launch；检查脚本 `scripts/verify-application-entrypoints.ts`）：

> 受支持的 Node 应用，只能通过命名的 `dsh` profile 启动。  
> 各包自己的可执行文件、演示、在本进程里直接挂插件、私有的浏览器预览，都不算正式入口。

## 3. 功能包怎么组织

### 3.1 命名与位置

- npm 包名：`@deepseek-ai/dsh-<名字>`；vendor 里的框架也是 `@deepseek-ai/…`（对照表见 `docs/rescope.md`）。
- 磁盘：`packages/<分组>/<包>/`；一个包只属于一个分组；新包优先进已有分组。
- 每个 harness 包都把 `@deepseek-ai/cordis` 声明为「同进程需要的对等依赖」。

### 3.2 包大致分几类

| 类型 | 白话 | 例子 |
| --- | --- | --- |
| 插件 / 服务 | 被加载器挂进运行环境，对外提供能力 | 多数功能包 |
| 库 | 给启动器或工具调用，不是用户直接敲的产品命令 | `dsh-app-boot` |
| 功能组合包 | 主要交付配置补丁，把一堆插件排好序装上 | `dsh-base` |
| 能力一族 | 常拆成：接口定义、具体实现、给模型用的工具 | `fs/`、`shell/`、`llm/` |

注册习惯（见根目录与 `packages/AGENTS.md`）：

- 注册工具、监听事件要用可撤销的方式（`ctx.effect()` / `ctx.on()`）；卸载插件时应能干净拆掉。
- 依赖哪些服务，用 `inject` 声明，不要手写「谁必须比谁先启动」。
- 可选服务用 `ctx.get(名字)`；已经声明注入的才能当 `ctx.某服务` 用。
- 扩展代码应依赖**接口**，不要绑死某一种实现；主循环插件也可以换。

### 3.3 包内工程习惯

- TypeScript 配置：服务端风格用 `tsconfig.base.json`，浏览器端用 `tsconfig.base.client.json`；源码在 `src/`，类型输出到 `lib/types`。
- 若同一包既有 Node 端又有浏览器端，常拆成 `tsconfig.host.json` / `tsconfig.client.json` 两套，根配置只负责串起来。
- 测试放在包下的 `tests/`，不要塞进 `src/__tests__/`。
- 用户能感知的插件，要用「真的用加载器读配置文件」的集成测试，不能只在测试里手动 `ctx.plugin(...)` 假装集成过了。

分组总表见 `packages/README.md`。

## 4. 有哪些「产品入口」

| 入口 | 代码位置 | 怎么启动 |
| --- | --- | --- |
| 命令行 `dsh` | `apps/cli` | **唯一公开的 Node 正式入口** |
| 网页 | 服务端在 `packages/host/*`，浏览器端在 `packages/client/*`，组合在 `dsh-web-app`；前端工程在 `apps/web` | `dsh web` 或 `--profile web` |
| 桌面 | `apps/desktop` + `apps/desktop-host` | Electron 里用 Node 模式拉起与 CLI 共用的启动逻辑 + 完整网页；配置目录独占 `profiles/desktop` |
| 启动辅助库 | `packages/boot/…` | 不是给用户直接敲的产品命令 |
| TypeScript SDK | `packages/sdk/…` | 客户端**再启动一个** `dsh --profile sdk` 子进程 |
| Python SDK | `python/sdk` + `python/sdk-runtime` | 安装包里带 `dsh`；默认 `sdk`，最小例子用 `sdk-minimal`；必须明确指定数据目录（Harness home） |
| ACP | `packages/acp` + `dsh-acp-app` | `dsh --profile acp` |

桌面与命令行可以**共用** `$DSH_HOME` 里的会话等产品数据，但**不共用**各自的可执行文件、激活选择和依赖锁文件。公共命令行**不能**管理桌面专用的 profile。

## 5. 构建与测试怎么分

### 5.1 构建

- 服务端库：`tsc` 按 `tsconfig.host.json` 编译类型，再用 `tsdown` 打运行时代码（`host` 面）。
- 浏览器库：同理走 `tsconfig.client.json` 与 `client` 面。
- 总构建入口：`tsx scripts/build.ts`；本地系统模块另有 `build:native-system`。
- 开发时可用 tsx 直接跑源码；发布路径走编好的 `lib/`。

### 5.2 测试命令（各自干什么）

| 命令 | 干什么 |
| --- | --- |
| `pnpm run test` | 日常单元测试 |
| `pnpm run test:coverage` | **CI 认的覆盖率检查**（比普通 `test` 更严） |
| `pnpm run test:e2e` | 打真实 API；没有 `DEEPSEEK_API_KEY` 会自动跳过 |
| `pnpm run test:expected` | 各包自己维护的「进程输出应对得上」类测试 |
| `pnpm run test:snapshot` | 用录好的会话回放（不需要 key）；必须走正式 profile |
| `pnpm run test:docs` / `doc-sync` | 文档快速检查 / 完整文档检查 |
| `pnpm run hygiene` | 发布包格式、工作区依赖、类型消费方式等卫生检查 |

`snapshots/` 只放会话回放用例；不要另开旁路入口。回放对不上时，优先改测试数据，不要先改「抹平差异」的规范化逻辑。推代码前按 `.agents/skills/dsh-pre-push-checks` 只跑和本次改动相关的检查，不必默认跑全仓库。

## 6. 加功能默认往哪加（尽量别改主循环）

### 6.1 「能力三件套」

仓库把一项可替换能力叫作完整的一套：

1. **接口**（Service Definition）：规定别人能调什么；  
2. **实现**（Provider）：真正干活的那份代码；  
3. **使用方**（Consumer）：常常是给模型调用的工具。

换一套实现，往往整条链一起换。例如把执行环境指到远程沙箱，命令行、终端、语言服务往往会一起走远程。详见 `docs/architecture.md` 与 `docs/capability-seams.md`。

### 6.2 三类事件

| 类型 | 干什么 |
| --- | --- |
| 会话事件 | 写进持久日志；**给模型看的内容必须能从日志还原** |
| Agent 事件（`agent/…`） | 任务进行中观察或拦截 |
| 能力事件（`fs/…`、`tools/…` 等） | 给文件系统、工具等加策略，不必引用主循环代码 |

有一类「瀑布」事件（请求前后、流式输出、工具执行前后）：监听函数必须调用 `next()` 把控制权交给下一环，否则等于直接截断。一轮对话怎么走，见架构文档里的 Turn flow。

### 6.3 常见需求对照

| 你想做的事 | 优先挂哪里 |
| --- | --- |
| 新的大模型提供方 | `ctx.llm` 上注册适配器 |
| 新的模型工具 | `ctx.tools` |
| 某个会话用不同工具集 | Agent 预设，需要隔离时用隔离域 |
| Shell / 终端 / 文件 / 沙箱 / 后台任务 / Webhook | 对应的 `ctx.…` 与相关事件 |
| 拦截请求、工具或一轮对话 | `agent/…` 或 `tools/…` 事件 |
| 需要长期保存的状态 | 扩展会话事件类型，并保证能回放 |
| 界面 | 驱动 `ctx.agents`，按会话事件渲染；聊天节点挂在 Client 侧 |

**默认不要改 `agent-loop`（主循环）。** 新行为应挂在已有扩展点上；若必须改主循环，同一变更里要更新 `docs/architecture.md`。动手指南见 `docs/cookbook/extension-cookbook.md`。

## 7. 文档与给 Agent 用的说明怎么分层

| 层 | 放哪 | 干什么 |
| --- | --- | --- |
| 全局常驻规则 | 根目录 `AGENTS.md`（`CLAUDE.md` 指向它） | 每次会话都要守的短规则，细节链到别处 |

| 架构总图 | `docs/architecture.md` | 改 `packages/` 前应先读 |

## 8. 做 fork / 二次开发时优先注意

1. **Cordis 是拷进 `vendor/` 再打补丁的**，不是随便升级 npm 版本；同步上游要按 `vendor/README.md` 的修改清单重做。  
2. **产品轴心是 profile + 功能组合包**；正式入口只能是 `dsh`。  
3. **桌面与命令行是两条轨**：桌面独占 `profiles/desktop`，可执行文件与锁文件分开。  
4. **DeepSeek 相关插件挂在共用底座里**；要去品牌或白标，从功能组合包的补丁层改。  
5. **TypeScript / Python SDK 都是再启动一个 dsh**，不是在 SDK 里嵌第二套完整运行时。  
6. **文档检查很多**；关掉检查后，文档很容易和代码脱节。  
7. **服务端与浏览器端分开编译**，这是一等公民，不是事后补丁。

## 10. 结构简图

```text
                 仓库根目录（pnpm 多包）
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
     packages/        apps/        vendor/
   （功能与组合包）  （cli/网页/桌面） （Cordis 源码）
          │             │
          │      dsh --profile 某名称
          │             │
          └────► 启动库叠配置 ◄────┘
                       │
                       ▼
              Cordis 加载出的插件树
           （服务、事件、可撤销注册）
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
      网页服务      无界面跑一次    SDK / ACP 服务
      + 浏览器界面                 （进程通信）
```
