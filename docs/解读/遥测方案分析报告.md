# DeepSeek Harness 遥测方案分析报告

> 阅读日期：2026-09-21  
> 这份笔记回答：遥测**是什么**、**默认发不发**、**发什么**、**发到哪**、**怎么关**，以及它和「跟 DeepSeek 请求一起带的会话日志」有何不同。  
> 依据：`packages/session/session-telemetry*`、`packages/identity/anonymous-user-id`、`packages/bundle/base/cordis.patch.yml`、`apps/cli/reference/README.md`、`docs/user/guide/network-proxy.md`。  
> 性质：解读笔记，非产品权威。`SAFETY.md` **未**专章写遥测。

## 先记住这一段

仓库里常说的「遥测」，指的是：把**会话日志的一份副本**，用业界常见的 **OpenTelemetry（简称 OTel）日志协议**，经 HTTP 发到采集端点。

默认策略是 **「只有你主动反馈之后才上传」**（模式名 `FEEDBACK_ONLY`）：

- 平时跑任务、调模型 → **不会**因此发遥测；  
- 你提交反馈（文字反馈、消息评分、改备注、撤回等）→ 才授权上传「到这次反馈为止」的那段日志；  
- 想彻底不发 → 设环境变量即可。

它和另一条通道 **不是一回事**：

| 通道 | 白话 | 默认 |
| --- | --- | --- |
| **OTel 会话遥测**（本文重点） | 独立 HTTP，发到遥测采集站 | 反馈后才发 |
| **DeepSeek 请求旁路日志**（`session-log-deepseek`） | 跟在 DeepSeek 模型请求里当元数据字段 `dsh_session_log` | 默认开，跟请求走 |

关掉其中一条，**不会**自动关掉另一条。

## 1. 由哪些包负责

| 包 | 干什么 |
| --- | --- |
| `@deepseek-ai/dsh-session-telemetry` | 定义「会话遥测」能力：从会话里抓记录、可挂脱敏规则 |
| `@deepseek-ai/dsh-session-telemetry-otel` | 真正往外发的实现：用 OTel 的「日志导出」 |
| `@deepseek-ai/dsh-anonymous-user-id` | 本机生成并保存一个匿名 UUID，随遥测批次带上 |
| `dsh-app-boot`（启动库） | 若设置了 `DSH_TELEMETRY_DISABLED`，启动前直接禁用遥测插件行 |
| `dsh-base`（共用底座） | 默认挂上 OTel 遥测插件，并写入默认端点与模式 |

谁装了共用底座（网页 / 无界面 / SDK 常用版 / ACP），一般就带上遥测插件。  
**最小 SDK**（`sdk-minimal`）故意不叠底座，**不含**这条 OTel 遥测（但仍可能有 `session-log-deepseek`，那是另一条通道）。

## 2. 默认行为：什么时候会出网

| 模式 `mode` | 行为 |
| --- | --- |
| `FEEDBACK_ONLY`（底座默认） | 仅在**本会话新的显式反馈**之后，上传「尚未交出去、截止到该反馈」的日志前缀；之后的记录要等下一次反馈 |
| `DISABLED` | 不建导出管道；**没有**遥测记录离开本机 |
| `FULL` | **不接受**；写了会配置失败，不是「全量常开上传」 |

**不会**单独因为下面这些事情就上传遥测：

- 普通模型请求、恢复会话、插件热更新、仅「磁盘上已有旧反馈」  
- 子会话继承父会话的反馈（子会话要自己再反馈一次才授权）  
- 代码里直接调用 `ctx.sessionTelemetry.emit()`（在当前 OTel 实现里等于空操作，绕不过反馈门）

授权之后，SDK 的定时批量发送或进程退出前的冲刷，可以**把已经授权的批次发完**，不必再点一次反馈或再跑一轮模型。

反馈本身先写进**本机会话日志**，并不等于「已经成功传到云端」；界面上的「已记录」只保证本地记了。

## 3. 上传的内容是什么

在允许上传的模式下，发出去的是会话事件里的数据副本，可能包括例如：

- 消息正文  
- 工具参数与结果  
- 系统提示与工具描述  
- todo、压缩摘要、反馈文字  
- 会话工作目录（`cwd`）等  

**结构上不会进遥测的：**

- 模型提供方的 API Key（它是适配器构造参数，不是会话事件）

**默认没有内置脱敏。** 若部署方要抹掉敏感字段，需自己在遥测流水线上挂规则（`session-telemetry/record` 一类扩展）。不挂规则时，出站内容和捕获内容一致。

其它过程特性（官方 README 也写了）：

- 尽量不阻塞主流程；尽力发送，崩溃可能丢队列；可能重复；接收方宜按会话 id、格式版本、事件序号去重。  
- 「交接成功」不等于「对端一定持久保存好了」。  
- 本地删掉反馈事件，**不会**自动擦除已经发到远端的数据。

## 4. 发到哪里、怎么发

| 项 | 默认 / 说明 |
| --- | --- |
| 协议 | OTLP：**用 HTTP 发日志**（不是随便自定义私有协议） |
| 默认地址 | `https://harness-telemetry.deepseeksvc.com/v1/logs` |
| 可用覆盖 | 环境变量 `DSH_TELEMETRY_OTLP_URL`，或配置里改 `exporter.url` |
| 压缩 | gzip |
| 超时（底座默认） | 单次导出约 1s；批处理间隔约 10s；关闭等待外层约 3s |

**与代理的关系：** 遥测故意走 Node 自带 HTTP，**不走** DSH 给你配的全局 HTTP 代理。在「禁止直连外网、只许走代理」的环境里，遥测往往会失败；**产品功能不依赖遥测是否成功**。需要彻底安静时，用下面的关闭方式。

依据：`docs/user/guide/network-proxy.md`、`packages/util/http-proxy/README.md`。

## 5. 匿名身份

| 项 | 说明 |
| --- | --- |
| 文件 | `$DSH_HOME/.anonymous-user-id`（常见是 `~/.dsh/.anonymous-user-id`） |
| 内容 | 一行随机 UUID；没有则创建 |
| 用途 | 出现在 OTel 资源属性 `user.id`（按批次带，不是登录账号） |
| 重置 | 删掉该文件，下次启动会生成新的 |

另外：发往 DeepSeek **模型 API** 时，还可能带请求头 `x-deepseek-harness-user-id`（同一套匿名 id 库）。那是模型请求侧行为，**开关与 OTel 遥测模式独立**。

## 6. 怎么关闭、怎么改配置

### 环境变量（最常用）

| 变量 | 作用 |
| --- | --- |
| `DSH_TELEMETRY_DISABLED=<任意非空>` | **最硬**：启动器直接禁用遥测插件行（连 `'0'` / `'false'` 也算「非空」，一样关闭） |
| `DSH_TELEMETRY_MODE=DISABLED` | 插件可加载，但不建传输，不外出 |
| `DSH_TELEMETRY_MODE=FEEDBACK_ONLY` | 明确使用「反馈后才传」（与默认相同） |
| `DSH_TELEMETRY_OTLP_URL=https://…/v1/logs` | 改采集地址（须是完整 http/https 日志端点） |
| `DSH_TELEMETRY_MODE=FULL` | **无效 / 被拒绝**，不要指望靠它开「全量上传」 |

CI 里常见会设 `DSH_TELEMETRY_DISABLED=1`，避免测试流量打到生产采集站。

### 配置文件（profile 补丁）

可改 `session-telemetry-otel` 这一行的 `mode`、`exporter`、`processor` 等。示意见包 README：

```yaml
- id: session-telemetry-otel
  name: '@deepseek-ai/dsh-session-telemetry-otel'
  config:
    mode: DISABLED
    # 或 FEEDBACK_ONLY，并配置 exporter.url
```

注意：要用「行被禁用」那种最硬关闭时，依赖启动器对 `DSH_TELEMETRY_DISABLED` 的处理；单靠改 config 字段有时关不掉「行本身是否启用」。

### 和另一条通道分开关

| 你想关的 | 做法 |
| --- | --- |
| OTel 遥测 | `DSH_TELEMETRY_*` 如上 |
| DeepSeek 请求旁路日志 | 在补丁里设 `session-log-deepseek` 的 `enabled: false`（包名 `@deepseek-ai/dsh-session-log-deepseek`） |

## 7. 和「DeepSeek 会话日志旁路」怎么区分

```text
本机会话日志（权威、始终在本地）
        │
        ├──► OTel 遥测（可选）──HTTP──► harness-telemetry…/v1/logs
        │         触发：显式反馈（默认）
        │
        └──► session-log-deepseek（可选）──附在 DeepSeek 模型请求里
                  触发：后续带会话的 DeepSeek 调用
                  成功后本地记 delivery-accepted 水位
```

| 对比项 | OTel 遥测 | session-log-deepseek |
| --- | --- | --- |
| 去哪 | 独立采集站 | DeepSeek API 请求元数据 |
| 何时 | 反馈门控（默认） | 跟模型请求 |
| 适用对象 | 所有用户 / 提供方（含官方） | 走 DeepSeek 适配器的请求 |
| 投递确认 | 无产品级「对端已收」回执 | HTTP 成功后写本地水位事件 |
| 是否进模型对话正文 | 否 | 否（只增加请求体积） |

两条可以同时开，内容可能重叠，但彼此独立。

## 8. 流程简图

```text
用户使用 Agent（本机）
        │
        ▼
   会话事件写入本地日志
        │
        ├── 无新反馈 ──► 不发 OTel
        │
        └── 用户提交反馈（评分 / 文字 / 撤回等）
                    │
                    ▼
           授权：可导出「到此反馈为止」的前缀
                    │
                    ▼
           （可选）脱敏规则改写副本
                    │
                    ▼
           OTel 批量 / 退出前冲刷
                    │
                    ▼
           HTTPS → 采集端点
           （带匿名 user.id；不走 DSH 代理）
```

## 9. 对 fork / 二次部署的实用建议

1. **先分清两条通道**：关遥测不等于关 DeepSeek 旁路日志。  
2. **内网只出代理、禁直连**：遥测会失败；要么接受失败，要么 `DISABLED` / `DSH_TELEMETRY_DISABLED`。  
3. **要自建采集**：改 `DSH_TELEMETRY_OTLP_URL` 或配置 `exporter.url`，并自行做脱敏与留存策略。  
4. **最小 SDK 场景**：默认没有 OTel 插件，但仍可能有旁路日志——按需关 `session-log-deepseek`。  
5. **不要假设 `FULL` 还可用**：当前实现只认反馈门控或关闭。
